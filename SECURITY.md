# Security Policy / Политика безопасности

## Поддерживаемые версии

| Версия | Поддержка |
|--------|-----------|
| 1.3.x  | активная  |
| 1.2.x  | безопасность (только фиксы CVE) |
| < 1.2  | не поддерживается |

## Как сообщить об уязвимости

Пожалуйста, НЕ публикуйте уязвимость в публичных issue и PR.

1. Используйте приватное уведомление GitHub: вкладка **Security → Report a vulnerability** (private vulnerability reporting).
2. Если это невозможно — напишите владельцу репозитория напрямую (email из профиля).

Что прислать:
- описание проблемы и сценарий воспроизведения;
- затронутую версию (help → about / `CARGO_PKG_VERSION`);
- при возможности — PoC или логи; не прикладывайте реальные пароли и содержимое сейфов.

Сроки ответа: первичная реакция — до 72 часов, оценка — до 7 дней, выпуск исправления зависит от сложности (критические — в приоритете). Мы crediting репортёров по их желанию в релизных заметках.

## Область (scope)

- `src-tauri/` — ядро (криптография, формат сейфа, локальный HTTP API на 127.0.0.1:5149, named pipe / unix socket, native messaging);
- `src/` — фронтенд (сторы, компоненты);
- `extension/` — браузерное расширение и native-host.

Не является уязвимостью: отказ в обслуживании на локальном пользователе, «уязвимости» требующие физического доступа к уже разблокированной сессии, отчеты от статических сканеров без демонстрации воздействия.

## Безопасность дизайна (кратко)

- Argon2id (64 MB, t=4, p=2, мигрируется со старых 16 MB / t=3 при unlock) → HKDF-SHA256 → двойной AEAD: XChaCha20-Poly1305 (заголовок) + AES-256-GCM (payload), AAD-привязка блоков к ролям (v2);
- decoy-слот (правдоподобное отрицание), hw-key (флешка с keyfile), слепой буфер (секрет не попадает в системный clipboard);
- бэкенд-автоблокировка: секреты затираются по простою независимо от фронтового таймера;
- файл сейва пишется атомарно (tmp → fsync → rename) с предыдущей копией в `.safepass.bak`.

## Что утекает без мастер-пароля (threat model)

Файл `.safepass` зашифрован по схеме «Argon2id(salt) → HKDF → XChaCha20». Без мастер-пароля атакующий, получивший файл и `.safepass.dk` (device key), может извлечь **только метаданные**:

- размер payload (количество байт, грубая оценка количества записей);
- размер каждого decoy-слота (но не отличить «спящий» от «активного»);
- timestamp `created_at` / `modified_at` из зашифрованного inner header — **нет, не извлекается** (зашифровано), но `chrono::now()` используется как `salt` в `Argon2id`, что **детерминированно на одной и той же машине**;
- `kdf_params` (memory_kb, iterations, parallelism) — публичное поле заголовка;
- `hw_key.keyfile_id` — публичное поле заголовка, нужно для поиска файла на диске.

Что **НЕ** утекает без ключа:
- заголовки записей, URL, username, password, notes, TOTP, custom fields;
- содержимое вложений;
- decoy-данные (если открыт другой слот).

**Следствие:** `entry_count` в inner header ограничен разумным пределом (1 млн) — даже если злоумышленник с мастер-паролем попытается записать `entry_count: u32::MAX`, после перешифровки оно saturate'ится.

## KDF migration (1.2.x → 1.3.x)

Версии 1.2.x создавали vault-файлы с `Argon2id(16 MB, t=3, p=2)`. Начиная с 1.3.x, `KdfParams::default()` = `Argon2id(64 MB, t=4, p=2)`. При первом успешном unlock на новой версии параметры автоматически поднимаются — заголовок перешифровывается с новой солью, payload остаётся нетронутым. Это **прозрачно для пользователя**, но первый unlock на старом vault занимает чуть больше времени (~250 мс → ~1 с на средней машине).

Миграция **только для настоящего (не decoy) слоя**. Ложный слот при следующей переустановке decoy-пароля получает актуальные параметры автоматически.

## Защита памяти

- `SetUnhandledExceptionFilter` + `TerminateProcess` при необработанных исключениях: WER не успевает снять crash-dump с чувствительными ключами.
- `SetErrorMode(SEM_FAILCRITICALERRORS | SEM_NOGPFAULTERRORBOX | SEM_NOOPENFILEERRORBOX)`.
- `SeLockMemoryPrivilege` для расширения квоты `VirtualLock`.
- `SetProcessWorkingSetSize(MAX)` после обнуления секретов — вытесняет страницы в файл подкачки, **уже стёртые**.
- `panic = "abort"` в `[profile.release]` — последняя линия защиты от панических дампов.

## Device key (second factor)

Device key (16 случайных байт) — второй фактор «привязка к машине». С v1.3.x основное хранилище — **Windows Credential Manager** через keyring crate (тот же keyring, что и для biometry). Fallback — файл `.safepass.dk` рядом с vault-файлом, для portable-сценариев.

**Утечка обоих файлов + KDF 16 MB / t=3** позволяла офлайн-перебор за часы. Сейчас:
- keyring-путь требует доступа к HKCU текущего пользователя (другой user не прочтёт);
- KDF 64 MB / t=4 даёт запас в ~4× против GPU-ферм.

## CSP и веб-безопасность

- `script-src 'self' 'unsafe-eval'` в dev-режиме (нужно для Vite HMR).
- В production `'unsafe-eval'` автоматически снимается `build.rs` (флаг `MYNX_STRIP_CSP=1`, см. `npm run tauri-build`).
- `connect-src 'self'` запрещает прямые внешние HTTP-запросы из вебвью; фавиконки и т.п. идут через Rust-команду.

## Подпись бинарников (externalBin pinning)

- `mynx.exe` и `mynx-native-host.exe` подписываются одним и тем же Authenticode-сертификатом через `scripts/release.ps1` (`Set-AuthenticodeSignature` + timestamp).
- Native host помимо проверки ОС-уровневой Authenticode-подписи (другой user / процесс не сможет подменить) **сверяет SHA256** исполняемого `mynx.exe` с константой `EXPECTED_MYNX_SHA256` в `src/native_host.rs`. Константа патчится на этапе `release.ps1` ПОСЛЕ подписи mynx.exe (порядок важен — подпись меняет хеш).
- Если бинарь переподписан валидным (например, украденным) сертификатом — хеш не совпадёт, native host откажется работать. Это второй уровень защиты поверх OS-level Authenticode.
